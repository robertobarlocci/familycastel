# 2026-08-11 — A public landing page for Family Castel, on GitHub Pages

## Goal

Family Castel has no public face. `https://robertobarlocci.github.io/familycastel/` is a
404, Pages is not enabled, and the repository has neither a description nor a homepage URL
(`.claude/cache/reproduction.md`, `BASELINE-CONFIRMED`). Anyone who hears the name and
searches for it finds, at best, a raw GitHub repo.

Ship a single, fast, self-contained marketing page that:

1. **Sells the product to the people who decide** — parents — and **appeals to the people
   who use it** — children. The product's own design rule applies to its website too
   (`README.md:16`): *if a screenshot looks like admin software, the design is wrong.*
2. **Explains the name.** "Family Castel" is one L on purpose, said the Spanish way —
   *cas-TEL*. It is the first thing everyone asks, it is the most memorable thing about the
   brand, and it is a natural search query. It gets its own section, its own anchor and its
   own FAQ entry.
3. **Is found on Google.** Complete, valid, non-duplicated metadata: a unique title and
   description, a canonical URL, Open Graph and Twitter Card tags, `SoftwareApplication` +
   `FAQPage` JSON-LD, `robots.txt`, `sitemap.xml`, semantic headings, and descriptive alt
   text on every image.
4. **Deploys itself** from `main` via GitHub Actions, so the site is never hand-published.

## Surgical scope

Limited to exactly the operator's request: a fun, SEO-strong landing page for Family
Castel, deployed on GitHub Pages, that explains the "Castel" spelling. Everything ships in
a new top-level `site/` directory plus one new workflow and one new test. **No file of the
running application is touched** — no PHP, no view, no `public-assets/`, no `sw.js`, no
`VERSION`.

**Out of scope** (tempting, deliberately excluded):

- A custom domain / `CNAME`. The operator asked for GitHub Pages; a domain is a purchase
  and a DNS decision that is theirs to make.
- Analytics, cookie banners, or any third-party script. The product's own promise is
  "no advertising, no analytics, nothing shared" (`lang/en.php:118`) — a tracker on its
  marketing page would contradict the pitch on the page.
- A documentation site, a blog, versioned docs, or a static-site generator. One page.
- Translating the page to German. The product ships de + en, but a second language doubles
  the SEO surface (hreflang, two canonicals, two sitemaps) and was not asked for. Noted as
  a follow-up in *Risks*, not filed as an issue — it is a product decision, not a defect.
- Changing `README.md`, the release pipeline, or the `.htaccess` deny list.
- Adding `site` to `ReleaseBuilder::DIRS`. It must stay out of the ZIP; see *Edge cases*.

## What ships

### 1. `site/index.html` — one page, hand-written, no build step

No bundler, no `node_modules`, no framework. Two reasons beyond simplicity: CI runs
`find . -name '*.php' … | xargs -n1 php -l` over the whole tree and only excludes
**root-anchored** `./vendor/*` and `./node_modules/*`, so a `site/node_modules/` would be
linted and would break CI; and `.gitignore`'s `/node_modules/`, `/dist/`, `/build/` are
root-anchored too, so a build toolchain under `site/` would be committed by accident.

Structure, in DOM order:

| Section | Purpose |
|---|---|
| Skip link + `<header>` | Accessibility, brand lockup (🏰 + `Family&nbsp;Castel`), nav to the anchors |
| `<h1>` hero | The one-line promise + primary CTA (Download the latest release) and secondary CTA (View on GitHub) |
| **"Why Castel and not Castle?"** | The name explainer, `id="castel"` — see §2 |
| "How it works" | Sidequest → Coins + XP → level up → world grows → redeem rewards, as four steps |
| "For the kids" / "For the parents" | The two audiences, in their own words, using the product's real vocabulary |
| Screenshots | Real product screenshots with descriptive alt text |
| "What's inside" | Honest feature list |
| "Install it" | The real requirements and the real five-step install |
| FAQ | `<details>`/`<summary>`, mirrored exactly by the `FAQPage` JSON-LD |
| `<footer>` | MIT licence, third-party credits, security policy, repo link |

**Every claim on the page is checked against the code.** The research pass produced an
explicit list of things a marketing page would be tempted to claim that are *not* true of
this product; the page states the honest version of each:

- pre-1.0 (latest public release is v0.1.4) — the page says "early days, and honest about
  it", it does not say "stable" or "1.0";
- Apache + `.htaccess` specifically, **not** "works on any host";
- install needs a database created by hand **and** an ownership-proof step that requires
  FTP/file-manager access to read `storage/setup-token.txt` — "no shell needed" is true,
  "nothing but an upload" is not;
- German and English only, chosen **at install**, with no in-app switcher;
- an offline-friendly **shell**, not offline quest completion;
- an installable **PWA**, not a native/App Store app;
- **in-app** notifications only — no push, no email, no cron;
- backups are one-click and pre-update, **not** scheduled;
- achievements are **cosmetic** (no Coins);
- exactly **two** themes, and the truthful line is that adding one is content, not code;
- level cap **500**;
- MIT, "AS IS", no warranty and no support offering.

Copy is warm and playful for the kid-facing parts (the product's own strings are the source
— "Who is playing today?", "Choose your hero!", "The kingdom is peaceful… for now.") and
plain and concrete for the parent-facing parts.

### 2. The name section — the fun bit, and a real SEO asset

`<h2>Why "Castel" and not "Castle"?</h2>` at `#castel`, written to be quotable and to rank
for the exact query. Content, in the page's voice:

- It is spelled **Castel**, with one L, everywhere — a project rule, not a typo
  (`CONTRIBUTING.md:14`).
- **Say it the Spanish way: cas-TEL**, stress on the second syllable. Said out loud it
  sounds like a small, slightly grand place — which is exactly what a family is.
- It started as a mis-spelling that everybody in the family kept saying on purpose, and it
  stuck. A castle is a building; a *Castel* is *ours*.
- A genuine coincidence, clearly labelled as a coincidence, because it is too good to leave
  out: in Catalonia a **castell** is a human tower — a whole crowd standing on each other's
  shoulders, with the smallest, lightest child climbing to the very top. Nobody planned
  that. It is still the best possible picture of what this app is for.
- One practical line: the repository is `familycastel`, so the spelling is load-bearing —
  search for "Family Castel", not "Family Castle".

The same question appears in the FAQ and in the `FAQPage` JSON-LD, so it is eligible for a
rich result.

### 4. SEO and crawlability

In `site/index.html`'s `<head>`:

- `<html lang="en">`, `<meta charset>`, viewport, `<title>` (≤60 chars), meta description
  (50–160 chars), `<link rel="canonical">` to the absolute Pages URL, `theme-color`
  `#2b2f6b`, and the icon links.
- Open Graph: `og:type`, `og:title`, `og:description`, `og:url`, `og:image` (absolute),
  `og:image:alt`, `og:site_name`, `og:locale`.
- Twitter: `twitter:card = summary_large_image`, title, description, image, image alt.
- JSON-LD, two blocks: `SoftwareApplication` (name, description, `applicationCategory`,
  `operatingSystem`, `offers` at price 0, `license`, `softwareVersion`, `author`,
  `codeRepository`) and `FAQPage` whose questions and answers are **the same strings** as
  the rendered FAQ — a mismatch there is a structured-data violation, so the test asserts
  the pairing in both directions.
- `site/robots.txt` — allows everything, points at the sitemap absolute URL.
- `site/sitemap.xml` — the one URL, with `<lastmod>`.
- `site/.nojekyll` — stops GitHub's Jekyll pass from eating files, and makes the deploy a
  plain file copy.

### 5. Assets inside `site/`

- `site/fonts/*.woff2` — copies of the five self-hosted faces already in the repo
  (Fredoka 600/700, Nunito 400/700/800, SIL OFL 1.1, credited in the footer). Copied rather
  than referenced because the Pages artifact is built from `site/` alone.
- `site/icons/` — `icon.svg`, `icon-192.png`, `icon-512.png`, copied for the favicon and
  the social image.
- `site/screens/` — **not** committed. The Pages workflow copies `docs/screenshots/` into
  the artifact at deploy time, so the marketing screenshots are always the ones CI most
  recently generated from the demo family and can never drift from the product. The test
  asserts every `screens/…` reference resolves to a real file in `docs/screenshots/`.

### 6. `.github/workflows/pages.yml`

```yaml
on:
  push: { branches: [main], paths: ['site/**', 'docs/screenshots/**', '.github/workflows/pages.yml'] }
  workflow_dispatch:
permissions: { contents: read }       # workflow-wide floor; write scopes are per-job
concurrency: { group: pages, cancel-in-progress: false }

jobs:
  verify:                             # the deploy GATE — see below
    runs-on: ubuntu-latest
    permissions: { contents: read }   # runs composer; must never hold pages/id-token
    steps:
      - uses: actions/checkout@v6
      - uses: shivammathur/setup-php@v2
        with: { php-version: '8.3' }
      - run: composer install --no-interaction --no-progress
      - run: vendor/bin/phpunit --filter=LandingPageSeo --no-coverage

  deploy:
    needs: verify                     # nothing publishes unless the contract holds
    runs-on: ubuntu-latest
    permissions: { contents: read, pages: write, id-token: write }
    environment:                      # REQUIRED for a protected Pages deployment
      name: github-pages
      url: ${{ steps.deployment.outputs.page_url }}
    steps:
      - uses: actions/checkout@v6
      - name: Assemble the site
        run: |
          set -euo pipefail
          rm -rf _site
          mkdir -p _site
          cp -R site/. _site/                 # NOTE the `/.` — copies CONTENTS, not the dir
          mkdir -p _site/screens
          cp docs/screenshots/*.png _site/screens/
          # Assert the SHAPE of what is about to be published, not just that it is non-empty.
          for required in index.html styles.css robots.txt sitemap.xml .nojekyll \
                          icons/icon.svg icons/icon-192.png icons/icon-512.png; do
            test -s "_site/$required" || { echo "missing or empty: $required" >&2; exit 1; }
          done
          test "$(ls _site/fonts/*.woff2 | wc -l)" -eq 5
          test "$(ls _site/screens/*.png | wc -l)" -ge 10
      - uses: actions/configure-pages@v5
      - uses: actions/upload-pages-artifact@v4
        with: { path: _site }
      - id: deployment                        # id is what `environment.url` reads
        uses: actions/deploy-pages@v4
```

Four details are load-bearing rather than incidental:

- **The deploy is GATED on the tests.** `ci.yml` and `pages.yml` are separate workflows, and
  the repo ruleset requires a PR but sets **no required status checks** — so without this
  gate a merge could publish a page whose SEO contract is failing, and the red run would sit
  in a workflow nobody is looking at while the live site is already wrong. The `verify` job
  runs the landing page's own test before anything is uploaded, and `deploy` `needs:` it.
  It is deliberately *this* test rather than the whole suite: `pages.yml` fires on
  `site/**`, which cannot break the application, and re-running the full matrix here would
  duplicate `ci.yml` for no signal.
- **The assembly guards assert the published shape**, not merely "a file exists". Every
  file the page actually needs is checked with `-s` (present **and** non-empty), the five
  woff2 faces are counted, and the screenshot count has a floor. A `cp` that half-worked,
  an empty stylesheet, or a screenshots directory that CI failed to regenerate all fail
  here — before the artifact is uploaded — instead of becoming a live unstyled page.

- **`environment: github-pages` with the deployment step's `id`.** `actions/deploy-pages`
  runs against the protected `github-pages` environment; without the block the deployment
  is rejected, and without `id: deployment` the `environment.url` expression resolves to
  nothing and the run's environment link is empty.
- **`cp -R site/. _site/`, not `cp -R site _site/`.** The latter publishes
  `_site/site/index.html`, i.e. a 404 at the site root — a silent, plausible-looking
  failure. The three `test` lines after the copy turn any assembly mistake into a red run
  instead of a deployed empty page.
- **Least privilege:** neither existing workflow sets a repo-wide `permissions` default and
  `release.yml`'s `contents: write` is scoped to itself, so this block is required. With
  `contents: read` the job **cannot write to the repository** at all. Path-filtered so
  ordinary app commits do not redeploy; `concurrency: pages` prevents overlapping deploys.

### 7. `tests/Unit/LandingPageSeoTest.php`

`tests/Unit` is auto-discovered by `phpunit.xml`, so this runs in the `tests` matrix (PHP
8.2 + 8.3), the `coverage` job and `release.yml`'s `validate-and-test` with no
registration. `FC_ROOT` is the repo root. `phpunit.xml` sets `failOnRisky="true"` and
`failOnWarning="true"`, so every test asserts something and every file read is guarded by
`assertFileExists` first.

## Teilaufgaben

1. **RED — write `tests/Unit/LandingPageSeoTest.php` first**, against a `site/` that does
   not exist yet. Run `vendor/bin/phpunit --filter=LandingPageSeo` and confirm **every**
   test fails on the missing file, not on a PHP error.
2. **GREEN — `site/index.html` + `site/styles.css`**, plus `robots.txt`, `sitemap.xml`,
   `.nojekyll`, and the copied `fonts/` and `icons/`. Re-run the filter until green.
3. **The workflow** — add `.github/workflows/pages.yml`. Validate its YAML locally
   (`python3 -c 'import yaml,sys; yaml.safe_load(...)'`) since nothing else lints it.
4. **Verify** — full `vendor/bin/phpunit` green (regression guard: `ReleaseBuilderTest`
   must still pass, proving `site/` stayed out of the ZIP); `php scripts/build-release.php
   --out=dist` and assert the ZIP contains no `site/` entry; `find . -name '*.php' …
   php -l` clean.
5. **Final Playwright validation** — serve `site/` locally with the screenshots assembled
   exactly as the workflow does, then in a real browser: check the rendered page at 390px
   and 1280px, assert zero console errors, zero third-party requests, no horizontal
   overflow, that every image loads (no 404s) and that the JSON-LD parses.
6. **Docs — outside the repo.** Update the Coding Vault pages at
   `~/Coding-Vault/Coding/familycastle/`: `CHANGELOG.md`, `ARCHITECTURE.md`, `FILE_MAP.md`.
   Mandated by workflow §11 and hook-enforced at commit time. These files live **outside
   this repository**, so they are deliberately absent from *Scope* and *Files changed*,
   which list repo files only — they add nothing to the PR diff.
7. **Deploy, in this order** — the order matters:
   1. **Enable Pages FIRST** (Settings → Pages → Source = *GitHub Actions*), *before*
      merging. Enabling Pages does **not** retry a run that already failed, so a
      merge-triggered deploy against a Pages-less repo would fail with a Not Found and
      then sit there red until someone noticed.
   2. Merge the PR.
   3. Watch the `pages` run. If it was already burnt by step ordering, re-run it —
      `gh workflow run pages.yml --ref main` (that is what `workflow_dispatch` is in the
      trigger list for) — rather than pushing an empty commit.
   4. Load the **live** URL in a real browser and confirm the page, the images and the
      metadata are actually served (not merely that the run went green).
   5. Set the repository `homepage` + `description` so the site is linked from the repo
      itself — a real discoverability win, and reversible.

## Edge cases

- **`site/` must never enter the release ZIP.** `scripts/build-release.php` is a strict
  allowlist (`ROOT_FILES`, `DIRS = ['app','views','public-assets','lang']`), so a new
  top-level directory is excluded automatically and no edit is needed.
  `ReleaseBuilderTest::testZipContainsOnlyAllowlistedTopLevelEntries` asserts the ZIP's
  top-level set, and Teilaufgabe 4 proves it by building a real ZIP.
- **The `php -l` sweep.** No `.php` file is added under `site/`, and no build toolchain, so
  nothing new is linted. The one new PHP file is the test, which the sweep lints anyway.
- **`ServiceWorkerShellTest` does not see `site/`.** Its iterator is rooted at
  `FC_ROOT . '/views'` and skips non-`.php` files, so HTML under `site/` may contain
  `/public-assets/` literals freely. It also never gains a new precache entry, so INV-006's
  pairing is untouched (see below).
- **Jekyll.** Without `.nojekyll`, GitHub's Jekyll pass drops files beginning with `_`.
  Shipping it makes the deploy a literal copy.
- **A screenshot is renamed or deleted.** The page would show a broken image and nobody
  would notice. The test resolves every `screens/…` reference against `docs/screenshots/`,
  so a rename fails CI.
- **`prefers-reduced-motion`.** Every animation is inside the guard, matching the product.
- **Very narrow phones (320px).** The page is fluid from 320px; the Playwright pass checks
  for horizontal overflow at 390px and 320px.
- **`docs/` is served by the dev stack.** `docker/compose.yaml` bind-mounts the whole repo,
  so `site/` is browsable at `http://localhost:8090/site/` in dev. Harmless — `site/` never
  ships — and convenient for the validation step.

## Threat model

**Minimal, and worth stating precisely rather than waving away.**

- **Attack surface added to the product: none.** No PHP, no route, no query, no input
  handling, no authentication decision, no data flow. The application binary and the
  release ZIP are byte-identical before and after this change.
- **The page itself is static and has no inputs.** No forms, no query-string handling, no
  JavaScript that reads `location`, no `innerHTML`. The only script content is two
  `application/ld+json` blocks, which are data, not executed code.
- **No third-party requests.** Fonts, icons and CSS are same-origin; there is no CDN, no
  analytics, no embed. This removes the whole class of supply-chain and tracking risk, and
  it is also the honest position for a product whose own copy promises "no advertising, no
  analytics, nothing shared with anyone".
- **Outbound links** (`github.com`, the releases page, `SECURITY.md`) carry
  `rel="noopener noreferrer"` where they open in a new tab.
- **Workflow permissions** are least-privilege and explicit: `contents: read`,
  `pages: write`, `id-token: write`. It cannot write to the repository. It is
  path-filtered, and `concurrency: pages` prevents overlapping deploys.
- **Publishing risk, stated plainly:** this makes a previously unadvertised installation
  publicly discoverable and tells readers what the product does. It publishes no
  credentials, no host names and no personal data. The screenshots come from the **demo
  family** (Emma/Noah), which is synthetic seed data, not a real family — and the demo
  parent password that appears in developer docs is **not** placed on the page.
- **Residual risk:** GitHub Pages serves over HTTPS on a `github.io` subdomain; the site is
  public by definition. That is the intent.

## Invariants and lessons this plan is bound by

**INV-004 (HARD) — the product is spelled "Family Castel": preserved, and it is the
subject of an entire section.** Every occurrence on the page, in the metadata, in the
JSON-LD and in the page title uses **Castel**. The word "Castle" appears only inside the
explainer, as the thing the name is deliberately *not*, and in the FAQ question. The test
asserts this mechanically: `Family Castle` must appear **zero** times in `site/index.html`.
The quest feature is called **Sidequests** throughout, never Tasks/Chores/Missions —
also asserted.

**INV-006 (HARD) — emitted CSS/JS carries the version token, and the SW shell matches it:
not engaged, and deliberately kept that way.** The invariant governs assets the
*application* emits through `asset()`/`url()` and precaches in `sw.js`. This change adds no
file under `public-assets/`, emits nothing from any view, and adds nothing to
`VERSIONED_PATHS` or `STATIC_SHELL`, so the pairing pinned by `ServiceWorkerShellTest` is
untouched in both directions. `site/` is a separate static site on a different origin with
its own cache lifetime; the font and icon files there are **copies**, not the same URLs, so
they cannot collide with the app's precache entries. Confirmed by running the full PHPUnit
suite in Teilaufgabe 4.

**INV-003 (HARD) — production runs on plain shared hosting: preserved.** The release ZIP is
unchanged (the allowlist excludes `site/`), so what a parent uploads to cyon.ch-class
hosting is byte-identical. The landing page is *about* that constraint rather than a
violation of it, and it states the real requirements — Apache + `.htaccess`, PHP 8.2+,
MySQL/MariaDB, no shell — instead of implying it runs anywhere.

**Avoids LESSONS 2026-08-11 "Bumping VERSION locally 503s the dev stack".** That is
today's lesson, from the PR immediately before this one. This change deliberately does
**not** touch `VERSION`: the landing page is not part of the versioned application, and
its CHANGELOG entry belongs to the `0.1.5` section that PR #17 already opened. So there is
no `FC_VERSION` / `settings.app.version` divergence and the dev stack stays up. If the
stack ever 503s during this work, the first check is `curl -o /dev/null -w '%{http_code}'
http://localhost:8090/`, not the test output.

**LESSONS 2026-08-10 "File modes are program state" — does not apply.** It governs
`update.php`, which creates filesystem entries in a live install where PHP's uid differs
from the static-file server's. Nothing here runs on a customer host: `site/` is never in
the release ZIP, and the Pages artifact's modes are set by `actions/upload-pages-artifact`
and GitHub's CDN, not by this repository. The one adjacent property — "an asset that is
not world-readable 404s and looks like missing CSS" — is covered instead by Teilaufgabe 5,
which loads the assembled site in a real browser and fails on any image or stylesheet that
does not return 200.

**Avoids LESSONS 2026-08-10 "A shipped fix the browser never downloads".** Its general
form — *verify what the client actually received, do not infer it from the source* —
applies to a deploy too. Teilaufgabe 5 loads the assembled site in a real browser and
checks the delivered page (images resolve, no console errors, no third-party requests)
rather than trusting the HTML source, and Teilaufgabe 7 does the same against the **live**
Pages URL after deploy. A page that only renders on my disk is the same failure in a new
costume.

## Tests

`tests/Unit/LandingPageSeoTest.php` — one file, no new infrastructure. It parses
`site/index.html` with `DOMDocument` + `DOMXPath` (not regexes) so the assertions are about
structure rather than text.

1. **The page exists and has the structural basics** — `assertFileExists`; the source
   starts with `<!doctype html>`; `<html lang="en">`. Deliberately **not** described as
   "valid HTML5": `DOMDocument` silently repairs malformed markup, so it can prove the
   document parses and that specific nodes exist, but it is not a validator and this test
   must not claim to be one. Nor can a file-reading unit test say anything about how the
   document is *served* — only a response `Content-Type` could, and there is no response
   here. What it does prove is narrower and still worth having: the file is present, it
   declares an HTML5 doctype, and it declares its language — the parts the other twelve
   tests build on. Parse
   warnings are captured with `libxml_use_internal_errors(true)` and asserted to contain no
   `LIBXML_ERR_FATAL` entry, which is the strongest honest claim available here.
2. **Title and description are present and within SEO limits** — exactly one `<title>`,
   1–60 characters; exactly one `meta[name=description]`, 50–160 characters.
3. **Canonical URL** — exactly one `link[rel=canonical]`, absolute, `https://`, equal to
   the site's own URL constant.
4. **Open Graph and Twitter Card are complete, and no metadata is duplicated** — every
   required property present and non-empty; `og:image` and `twitter:image` are absolute;
   both carry alt text. Plus: **each of `<title>`, `meta[name=description]`,
   `link[rel=canonical]` and every `og:*` / `twitter:*` property appears exactly once.**
   Duplicated metadata is one of the commonest real SEO defects — crawlers pick one
   arbitrarily — and a page can grow a second `og:title` through an ordinary edit without
   any other test noticing.
5. **`SoftwareApplication` JSON-LD is valid AND complete** — the block parses as JSON, has
   `@context`/`@type`, and carries **every** field this spec promises, each asserted
   individually and non-empty: `name`, `description`, `applicationCategory`,
   `operatingSystem`, `offers.price === "0"`, `license`, `codeRepository`,
   **`softwareVersion`** (equal to the contents of the repo's `VERSION` file, so the page
   cannot advertise a version that does not exist — this is also the positive version pin
   that replaced the `"1.0"` denylist entry) and **`author`**. Naming a field in the spec
   and not asserting it is how a "complete" block quietly loses half its properties.
6. **`FAQPage` JSON-LD matches the rendered FAQ — questions AND answers, both directions,
   with counts.** Structured data that disagrees with the visible page is a Google policy
   violation, so "the questions line up" is not enough:
   - there are **at least 4** FAQ entries. Without a floor the whole test is vacuous: zero
     `<details>` and an empty `mainEntity` satisfy "equal counts" and both bidirectional
     comparisons perfectly;
   - the **count** of `mainEntity` entries equals the count of FAQ `<details>` elements
     (catches a question added to one side only, which a pure subset check would miss);
   - every `Question.name` equals the normalised text of its corresponding `<summary>`,
     and every `<summary>` maps back to exactly one `Question.name` — so duplicates on
     either side fail rather than silently pairing off;
   - every `acceptedAnswer.text`, after stripping tags and collapsing whitespace, equals
     the normalised text of that `<details>`' body. This is the half the first draft of
     this test omitted, and it is the half that actually breaks: a copy edit to a visible
     answer leaves the JSON-LD stale and nothing else would notice.
7. **Exactly one `<h1>`, and heading levels never skip** — `h1` → `h2` → `h3` order.
8. **Images: a floor, alt text, and every `src` resolving to a real file.** In order:
   - **at least 3 `<img>` elements, at least 2 of them under `screens/`** — without a
     floor the test passes on a page with no images at all, which is precisely the state a
     botched edit leaves behind;
   - every `<img>` has non-empty, non-whitespace `alt`;
   - every image `src` resolves on disk: `screens/…` against `docs/screenshots/` (the
     assembly the workflow performs), everything else against `site/`. A renamed or
     deleted screenshot fails CI instead of becoming a broken image nobody notices.
9. **No third-party requests — from every source that can make one, not just `src`/`href`.**
   A browser fetches from far more attributes than a naive scan looks at, and the ones it
   misses are exactly where a CDN font or a tracking pixel would hide. The test collects
   candidate URLs from **all** of:
   - the HTML: `src`, `href`, `srcset` (each comma-separated candidate), `poster`,
     `data-src`, `content` on `meta[http-equiv=refresh]`, `<source>`/`<track>`, and the
     ones an HTML-only scan usually forgets — **`object[data]`, SVG `xlink:href` / `href`
     on `<use>` and `<image>`, and `<a ping>`**;
   - **every `style` attribute** in the document, not just `<style>` blocks — an inline
     `background-image: url(https://…)` makes a request exactly like a `<link>` does;
   - **`site/styles.css` as well as the HTML** — every `url(...)` token and every
     `@import`, since a stylesheet is the most natural place for a remote font to sneak in
     and is invisible to any HTML-only check;
   - any `<style>` block, scanned the same way;
   - **`srcdoc`** on any `<iframe>` (an entire nested document, invisible to every
     attribute scan above).

   **No active embeds at all.** `<iframe>`, `<object>`, `<embed>`, `<frame>` and
   `<frameset>` are forbidden outright — asserted as a zero count, not scanned. A
   `srcdoc` iframe carries a complete nested document whose `<script>` elements never
   appear in the parent DOM, so counting scripts in the parent proves nothing about it;
   recursively parsing nested documents to apply the same rules is a lot of machinery for
   a page that has no reason to embed anything. Forbidding the elements is strictly
   stronger and one line.

   Two structural rules close what attribute scanning fundamentally cannot reach — a
   *runtime* request made by JavaScript, which no static scan can see:
   - **the page contains no executable script at all** — and "script" means every way a
     browser can run one, not just the element:
     - the only `<script>` elements permitted are the two `type="application/ld+json"`
       blocks; any `<script src=…>` or any script with an executable type fails;
     - **no `on*` attribute anywhere** (`onload`, `onerror`, `onclick`, …). An
       `<img onerror="fetch(…)">` executes with no `<script>` element in the document at
       all, so a script-element count alone is not the property being claimed;
     - **no `javascript:` URL in ANY attribute of ANY element** — the check walks every
       attribute of every node rather than the collected-URL list, because enumerating
       executable sinks is a losing game: `form[action]`, `button[formaction]`,
       `input[formaction]`, SVG `<a xlink:href>` and `<a href>` are all sinks, and the
       next HTML revision will add more. The value is trimmed, lowercased and
       percent-decoded before matching, and control characters are stripped, so
       `java&#9;script:` and `%6aavascript:` are caught too. A single general rule over
       all attributes has no list to keep up to date.

     The page genuinely needs no JavaScript, so all three cost nothing and together turn
     "no analytics, no third-party requests" from a promise into a structural fact.
   - **`site/styles.css` contains no `@import`.** Round 2 added recursive-import scanning;
     forbidding imports outright is simpler and strictly stronger, since a
     transitively-imported sheet can otherwise pull a remote font from a file the test
     never opened. One stylesheet, no indirection.

   Every collected URL must be a **document-relative** path (no leading `/`) or a `data:`
   URI. Root-relative is rejected too, not merely absolute: this is a **project** site at
   `/familycastel/`, so `/styles.css` resolves to the user's `github.io` root and 404s —
   a failure that only appears once deployed and looks like "the CSS is gone".

   Absolute URLs are allowed **only** on `<a href>` (outbound links to GitHub) and on the
   four SEO fields that are *required* to be absolute — `link[rel=canonical]`, `og:url`,
   `og:image`, `twitter:image` — each asserted **by name**, and each additionally asserted
   to start with the site's own canonical origin **and path prefix**, so "absolute" cannot
   become a hole through which a third-party image URL enters.
10. **INV-004 — "Family Castle" appears zero times** in `site/index.html`, and "Sidequest"
    appears at least once. The spelling rule, enforced rather than remembered.
11. **`robots.txt` and `sitemap.xml` must actually invite crawling.** Existence is not the
    property that matters — a `robots.txt` containing `Disallow: /` exists, names a
    sitemap, and defeats the entire point of the page. So:
    - `robots.txt` contains a `User-agent: *` group; that group has **no `Disallow:` rule
      that blocks `/`** (neither `Disallow: /` nor a rule whose path prefix covers the
      canonical page), and it names the **absolute** sitemap URL;
    - the page carries **no** `meta[name=robots]` with `noindex` or `nofollow`, and no
      `X-Robots-Tag` equivalent in a `meta[http-equiv]`. This is the other way a page
      silently de-indexes itself, and it lives in the HTML rather than in `robots.txt`;
    - `sitemap.xml` parses as XML, contains exactly one `<url>`, its `<loc>` equals the
      canonical URL exactly, and it has a **non-empty `<lastmod>`** in `YYYY-MM-DD` form.

11b. **INV-004 and the name explainer are enforced, not merely intended.** The "Castel"
    section is both a HARD invariant and the operator's headline request, so it gets
    assertions of its own rather than relying on a single spelling denylist:
    - an element with `id="castel"` exists, and it is (or contains) an `<h2>`;
    - that section's text contains **`Castel`**, the word **`Castle`** (it is explicitly
      about the contrast), and the pronunciation cue **`cas-TEL`**;
    - the FAQ contains a question whose text matches `/castel.*castle|castle.*castel/i`,
      so the explainer is also in the structured data and eligible for a rich result;
    - `Family Castel` appears at least 5 times in the document;
    - **`Family Castle` appears zero times, matched case-INSENSITIVELY** — the round-2
      version of this rule was case-sensitive, so `family castle` in a sentence would have
      slipped straight through the guard for a HARD invariant;
    - `Sidequest` appears at least once, and none of `chore`, `task list`, `mission`
      appears as the name of the feature (INV-004's second clause).
12. **`.nojekyll` exists** — otherwise the deploy silently changes shape.

12b. **Every local URL resolves, and the stylesheet is actually linked.** Test 9 proves
    nothing points *off-site*; this proves everything that points *on-site* is real —
    the other half, and the one whose absence produces an unstyled live page:
    - exactly one `link[rel=stylesheet]`, pointing at `styles.css`, which exists and is
      non-empty (a page that simply forgot its stylesheet would otherwise sail through
      every other test);
    - **every** local URL collected by test 9 — from the HTML *and* from `styles.css`'s
      `url(...)`/`@import` — resolves to a real, non-empty file under `site/`, except
      `screens/…` which resolves under `docs/screenshots/` per the deploy assembly.
      This is what catches a mistyped font filename, which is invisible in the source and
      produces a silently different typeface in the browser;
    - the five expected woff2 faces and the three icon files are present.

    **URL normalisation is defined once and shared by tests 9 and 12b**, because "does this
    URL resolve?" is ambiguous otherwise and an ambiguous rule is one that silently passes:
    - strip the **fragment** and the **query** before resolving — `styles.css?x=1#y` is the
      file `styles.css`;
    - a **pure-fragment** reference (`#castel`, and the skip link's `#main`) is an in-page
      anchor, not a request: it is exempt from file resolution, but is instead asserted to
      match the `id` of an element that actually exists in the document. A dangling
      in-page anchor is a real defect and this is the only test that would see it;
    - **percent-decode** the path before touching the filesystem;
    - reject any path containing a `..` segment, and assert the resolved absolute path is
      **contained** within `site/` (or `docs/screenshots/` for `screens/…`) using
      `realpath()` — so a traversal cannot be "resolved" by accident;
    - `data:` URIs are exempt from resolution; `mailto:`/`tel:` are exempt and permitted
      only on `<a href>`.
13. **Honest-claim tripwire** — a short, deliberately narrow denylist of claims the
    research pass proved false for this product: `App Store`, `push notification(s)`,
    `works on any host`, `unlimited levels`. Matched **case-insensitively** with word
    boundaries, so casing changes cannot slip past. Each entry carries an inline comment
    naming the code that makes it false (e.g. *notifications are in-app only — there is no
    push, no email and no cron*), so a future reader can tell whether the rule still holds
    rather than deleting a line they do not understand.

    Scope was cut on purpose after review: a substring denylist is a blunt instrument that
    can reject truthful contextual copy, so it covers only phrases with **no honest use**
    on this page. `"1.0"` was dropped from the list for exactly that reason — it appears
    legitimately in "SIL Open Font License 1.1" and in version strings. The version claim
    is instead pinned positively: the page must contain the string from `VERSION`, so it
    can only advertise the version the repo actually is. This test is a tripwire, not a
    fact-checker; the real defence is the claim-by-claim audit recorded in §1.

## Risks

- **Low — Pages is not enabled yet**, so the first workflow run fails with a Not Found
  until Source = GitHub Actions is set. Teilaufgabe 7 does it before watching the run.
- **Low — the screenshots are assembled at deploy time**, not committed, so a local
  `file://` preview shows broken images. Deliberate (it keeps them from drifting), covered
  by test 8, and the validation step assembles them exactly as the workflow does.
- **Low — copied fonts and icons can drift** from `public-assets/`. They are licence-stable
  binaries that have not changed since the first release; the alternative (referencing the
  app's copies) is impossible, since the Pages artifact is built from `site/` alone.
- **Low — CI runs all four jobs on a docs-only PR** (no path filters in `ci.yml`). Wasteful
  but correct; adding filters would be scope creep and would weaken the app's own gates.
- **Follow-up, not a risk to this diff:** the page is English-only while the product ships
  German too. A German version needs `hreflang`, a second canonical and a second sitemap
  entry — a real piece of work and a product decision, so it is named here rather than
  half-done.
